# IP Management System 部署形式分析与决策报告

> 分析三种部署/使用模式对架构设计、数据存储、协作能力的影响，为技术选型提供决策依据。
>
> **日期**：2025-06-28

---

## 三种模式对比总览

| 维度 | 模式1：本地文件网页 | 模式2：桌面应用 (exe) | 模式3：Web服务端部署 |
|------|-------------------|---------------------|-------------------|
| **本质** | 静态HTML + 本地JSON | 桌面壳 + 内嵌后端 | 前后端分离 + 服务端数据库 |
| **启动方式** | 双击 index.html | 双击 exe | 浏览器访问URL |
| **数据存储** | 本地JSON文件 / IndexedDB | 本地SQLite / 文件 | PostgreSQL / 云端数据库 |
| **网络依赖** | 无 | 无 | 有（必须联网） |
| **后端服务** | 无 | 内嵌（Electron/Tauri） | 独立（FastAPI） |
| **多人协作** | ❌ 不支持 | ❌ 单用户 | ✅ 支持 |
| **文件访问** | 受限（浏览器沙箱） | 完整（原生API） | 通过服务端中转 |
| **安装成本** | 零 | 需安装/解压 | 零（客户端），需运维服务器 |
| **更新方式** | 替换文件 | 自动更新/重装 | 服务端热更新 |
| **数据安全** | 用户完全控制 | 用户完全控制 | 服务器托管 |
| **扩展能力** | 低 | 中 | 高 |

---

## 模式1：本地文件网页（直接打开 index.html）

### 架构形态

```
┌─────────────────────────────────┐
│  浏览器打开 index.html           │
│  ┌──────────────────────────┐  │
│  │ 纯前端 SPA（Vue/React）   │  │
│  │ - 画布渲染（Canvas/SVG）   │  │
│  │ - 数据逻辑（JS/TS）        │  │
│  │ - 状态管理（Pinia/Vuex）   │  │
│  └──────────────────────────┘  │
│              │                   │
│  通过 File API / IndexedDB      │
│  读写本地 .json / .xml 文件      │
│              │                   │
│  本地文件系统（IP定义、设计文件）│
└─────────────────────────────────┘
```

### 数据模型变化

当前基于 PostgreSQL + SQLAlchemy 的**关系型数据模型**必须完全重写为**JSON 文件模型**：

| 当前（模式3） | 模式1 等价物 |
|-------------|------------|
| `ip_entity` 表 | `ip_catalog.json`（IP定义数组） |
| `block_design` 表 | `designs/{name}.json`（每个设计一个文件） |
| `bd_cell` 表 | 嵌入在 design JSON 中 |
| `bd_connection` 表 | 嵌入在 design JSON 中 |
| `address_region` 表 | 嵌入在 design JSON 中 |
| Alembic 迁移 | 无（JSON Schema 版本控制） |
| 数据库事务 | 无（文件原子写入模拟） |

### 关键技术点

- **文件访问**：使用 File System Access API（Chrome 支持）或 `<input type="file">` 选择目录
- **数据持久化**：项目目录下保存 `.json` 文件（类似 Vivado 的 `.xpr` + `.srcs` 结构）
- **IP Catalog**：从本地 `ip_repo/` 目录扫描 JSON/XML 文件构建目录
- **导出产物**：直接生成 `.v` / `.tcl` 文件到本地目录

### 优点
- **零安装、零配置**：无需 Python、PostgreSQL、Docker
- **数据完全本地**：无需担心数据泄露或服务器宕机
- **离线使用**：没有网络也能工作
- **文件级版本控制**：设计文件可用 Git 管理

### 缺点
- **浏览器安全限制**：无法直接访问任意文件路径（需要用户选择目录）
- **性能受限**：大量 IP 时前端渲染卡顿
- **无协作**：无法多人同时编辑一个设计
- **功能受限**：无法运行复杂算法（地址分配优化、DRC规则引擎）
- **浏览器兼容**：File System Access API 仅 Chrome/Edge 支持

### 适用场景
- 个人快速查看/编辑 IP 定义
- 轻量级设计浏览工具（类似只读查看器）
- 作为模式2/3的辅助预览工具

## 模式2：桌面应用（exe）

### 架构形态

```
┌──────────────────────────────────────────┐
│  桌面应用窗口（Electron / Tauri / Native）│
│  ┌────────────────────────────────────┐  │
│  │ 渲染层：UI + 画布（同前端技术）      │  │
│  │ - Vue/React + Canvas/SVG            │  │
│  └────────────────────────────────────┘  │
│  ┌────────────────────────────────────┐  │
│  │ 主进程：内嵌后端服务                 │  │
│  │ - Node.js 或 Rust 后端              │  │
│  │ - 本地 SQLite 数据库               │  │
│  │ - 完整文件系统访问                  │  │
│  └────────────────────────────────────┘  │
│  本地文件系统（设计文件、IP库、生成产物）│
└──────────────────────────────────────────┘
```

### 两种技术路线

| 路线 | 技术栈 | 说明 |
|------|--------|------|
| **Electron** | 前端(Vue/React) + Node.js后端 + SQLite | 成熟生态，体积大（~150MB） |
| **Tauri** | 前端 + Rust后端 + SQLite | 轻量（~5MB），性能更好，但 Rust 学习曲线 |
| **PyInstaller** | 当前 Python 代码打包为 exe | 快速过渡，但体积大、启动慢 |

### 数据模型变化

- **数据库**：PostgreSQL → SQLite（本地文件数据库）
- **SQLAlchemy**：可保留，只需修改连接字符串为 `sqlite+aiosqlite:///project.db`
- **FastAPI**：可保留，Electron 主进程内启动 Python 子进程或 Node.js 重写
- **文件存储**：本地 `~/Documents/IP_Management/` 目录下

### 关键技术点

- **IP Catalog**：本地 `ip_repo/` 目录扫描，支持导入/导出 `.zip` IP包
- **项目文件**：`.ipd` 项目目录（类似 Vivado `.xpr`），包含设计 JSON + SQLite 数据库
- **导出产物**：直接写入用户指定的 RTL 目录
- **更新机制**：内置自动更新（检查 GitHub Releases）

### 优点
- **原生体验**：快捷键、右键菜单、拖拽文件、系统托盘
- **完整文件访问**：像 Vivado 一样直接操作文件系统
- **离线使用**：无网络也能完整工作
- **性能**：本地 SQLite 足够快，前端渲染流畅
- **数据本地**：用户完全控制数据位置

### 缺点
- **体积大**：Electron 应用通常 100MB+，Tauri 可做到 5MB
- **跨平台打包**：Windows/Mac/Linux 需要分别构建
- **更新维护**：需要自动更新服务器或手动下载
- **协作**：仍不支持多人实时协作（可共享项目文件但需手动合并）

### 适用场景
- **主力工具**：像 Vivado 一样作为工程师日常设计工具
- **企业内网**：无互联网环境的离线工作站
- **IP 封装**：本地 IP 开发、封装、验证的完整工作流

## 模式3：Web服务端部署（当前架构）

### 架构形态

```
┌────────────────────────────────────────────┐
│  浏览器访问 https://ipm.company.com         │
│  ┌──────────────────────────────────────┐  │
│  │ 前端 SPA（Vue/React）                   │  │
│  │ - 画布渲染、UI交互                      │  │
│  │ - 通过 HTTP API 与后端通信              │  │
│  └──────────────────────────────────────┘  │
│              │ HTTP / WebSocket              │
│  ┌──────────────────────────────────────┐  │
│  │ 服务端（Docker 容器）                   │  │
│  │ - FastAPI（Python）                     │  │
│  │ - PostgreSQL 数据库                     │  │
│  │ - 文件存储（对象存储/本地卷）            │  │
│  └──────────────────────────────────────┘  │
│              │                               │
│  云端/服务器（数据库、文件、计算资源）        │
└────────────────────────────────────────────┘
```

### 当前架构优势（已构建）

- **团队协作**：多用户同时编辑、评论、版本历史
- **集中管理**：企业级 IP 库统一管控、权限控制
- **计算扩展**：复杂 DRC、地址优化可在服务端高性能计算
- **数据安全**：服务器备份、审计日志、灾难恢复
- **随时随地**：任何设备、任何地点访问（VPN/公网）
- **CI/CD 集成**：与自动化构建流水线集成（自动生成 HDL、跑仿真）

### 缺点
- **网络依赖**：无网络无法工作（可离线缓存部分数据）
- **数据不在本地**：数据在服务器上，导出才能本地使用
- **运维成本**：需要服务器、数据库、备份、安全维护
- **延迟**：大设计文件加载有网络延迟

### 适用场景
- **企业级 IP 管理平台**：全公司统一 IP 库和设计管理
- **团队协作**：分布式团队、多人同时设计
- **云原生**：与 CI/CD、DevOps、云平台集成

## 三种模式对当前设计的影响差异

### 如果切换到模式1（本地文件网页）

**需要重写的内容**：

| 当前组件 | 变化 | 工作量 |
|---------|------|--------|
| PostgreSQL 数据库 | 完全删除，改为 JSON 文件读写 | 高 |
| SQLAlchemy ORM | 删除，前端用纯 JS 操作 JSON | 高 |
| FastAPI 后端 | 完全删除，纯前端实现 | 高 |
| Pydantic 模型 | 改为 JSON Schema + JS 校验 | 中 |
| 数据库迁移 | 删除 | 低 |
| Docker 配置 | 删除 | 低 |
| 测试框架 | 改为前端测试（Jest/Vitest） | 中 |
| 画布逻辑 | 保留前端部分，后端逻辑前移 | 高 |

**结论**：几乎等于**重写整个项目**，仅前端画布代码可复用。

### 如果切换到模式2（桌面应用）

**需要调整的内容**：

| 当前组件 | 变化 | 工作量 |
|---------|------|--------|
| PostgreSQL | 改为 SQLite（SQLAlchemy 支持） | 低 |
| FastAPI | 保留，内嵌到桌面进程（Python 子进程） | 中 |
| 前端 | 保留，放入 Electron/Tauri 壳 | 低 |
| 数据库迁移 | 保留，但目标改为 SQLite | 低 |
| 部署相关 | 增加桌面打包（Electron Builder） | 中 |
| 文件访问 | 从 HTTP 下载改为直接本地文件操作 | 中 |
| 更新机制 | 增加自动更新模块 | 中 |

**结论**：**平滑过渡**，当前后端代码可保留 80% 以上。

### 模式3（当前架构）继续发展

| 当前组件 | 发展方向 | 工作量 |
|---------|---------|--------|
| FastAPI | 扩展 API、增加 WebSocket | 持续迭代 |
| PostgreSQL | 增加索引、分区优化 | 持续迭代 |
| 前端 | 开发 SPA 画布界面 | 高（待开发） |
| 协作 | 增加实时同步、版本历史 | 中 |
| DevOps | 完善 CI/CD、Docker 编排 | 低 |

## 建议决策路径

### 推荐方案：**模式2 + 模式3 混合（双形态）**

```
┌─────────────────────────────────────────────────────┐
│              共享核心层（Python）                    │
│  ┌──────────────┐  ┌──────────────┐               │
│  │  IP Catalog  │  │ Block Design │               │
│  │  Service     │  │  Service     │               │
│  └──────────────┘  └──────────────┘               │
│  ┌──────────────┐  ┌──────────────┐               │
│  │  Connection  │  │   Address    │               │
│  │  Service     │  │   Service    │               │
│  └──────────────┘  └──────────────┘               │
└─────────────────────────────────────────────────────┘
           │                           │
           ▼                           ▼
┌────────────────────┐      ┌────────────────────┐
│ 模式2：桌面应用      │      │ 模式3：Web 服务端   │
│ - Electron 壳      │      │ - FastAPI HTTP      │
│ - 内嵌 SQLite       │      │ - PostgreSQL        │
│ - 本地文件系统       │      │ - Docker 部署       │
│ - 单用户离线         │      │ - 多用户协作         │
└────────────────────┘      └────────────────────┘
```

**实现策略**：
1. **核心层**：保持当前的 Python 服务层（Business Logic）**与存储无关**
2. **存储适配层**：抽象数据库接口，支持 SQLite（桌面）和 PostgreSQL（Web）
3. **前端**：同一套 Vue/React 代码，编译为 SPA（Web）或嵌入 Electron（桌面）
4. **部署**：
   - 桌面版：Electron + Python 后端子进程 + SQLite
   - Web版：FastAPI + PostgreSQL + Docker

### 快速验证路径（MVP → 完整）

| 阶段 | 目标 | 模式选择 | 说明 |
|------|------|---------|------|
| **MVP** | 验证核心概念 | 模式3（当前） | 后端 API + 简单前端，快速迭代 |
| **v0.5** | 可用工具 | 模式3 | 完整 Web 前端 + 服务端，团队协作 |
| **v1.0** | 产品化 | 模式2 + 模式3 | 桌面版 + 网页版，覆盖所有场景 |
| **未来** | 生态扩展 | 模式1（辅助） | 提供只读查看器作为辅助工具 |

## 技术选型建议

### 如果主要面向**个人工程师/离线场景** → 优先模式2

- 使用 **Tauri**（Rust + 前端）打包，轻量快速
- 核心 Python 逻辑通过 PyO3 绑定到 Rust，或直接嵌入 Python 运行时
- 数据存储用 SQLite，项目文件直接落本地磁盘

### 如果主要面向**企业团队/云端管理** → 优先模式3（当前）

- 继续使用当前 FastAPI + PostgreSQL 架构
- 开发 SPA 前端（Vue3 + Pinia + Canvas库）
- 未来可增加 Electron 壳作为桌面客户端（复用前端代码）

### 如果目标是**Vivado 插件/辅助工具** → 模式1 作为补充

- 提供一个纯前端的 `viewer.html`，加载 Vivado 导出的 `.json` 设计文件
- 无需后端，双击即可查看 Block Design
- 作为模式2/3的辅助预览工具

## 总结

| 模式 | 复杂度 | 工作量 | 适用场景 | 建议 |
|------|--------|--------|---------|------|
| **1. 本地文件网页** | 高（重写） | 最大 | 轻量查看、辅助工具 | 不建议作为主力，可作为补充 |
| **2. 桌面应用** | 中 | 中等 | 主力设计工具、离线使用 | **推荐作为最终产品形态之一** |
| **3. Web 服务端** | 低（已有） | 最小 | 团队协作、企业级 | **推荐优先发展，当前架构正确** |

**核心建议**：当前的模式3（Web 服务端）架构是正确的技术方向。在此基础上：
1. 先完善 Web 版（前端画布 + 后端 API）
2. 未来用 Electron/Tauri 将前端打包为桌面版，内嵌后端为本地服务
3. 数据层通过适配器同时支持 PostgreSQL（Web）和 SQLite（桌面）
4. 模式1 作为纯前端查看器，供用户快速预览设计文件

这样一套代码，三种形态，最大化复用率。
