# IP Management System 部署形式分析与决策报告

> 分析三种部署/使用模式对架构设计、数据存储、协作能力的影响，为技术选型提供决策依据。
>
> **日期**：2025-06-28
> **更新日期**：2026-07-01（已根据实际实现更新为模式1）

---

## 当前状态声明

**当前代码已实现为模式1：本地文件网页（纯前端）。**

- 无后端服务、无数据库、无 Docker
- 直接打开 `index.html` 即可使用
- 数据存储在项目目录下的 `data/*.json` 文件中
- 技术栈：原生 JavaScript ES6 Modules + HTML5 Canvas 2D + 原生 CSS

模式2（桌面应用）和模式3（Web 服务端）仅作为未来可能的发展方向，不在 v1.0.0 范围内。

---

## 三种模式对比总览

| 维度 | 模式1：本地文件网页 | 模式2：桌面应用 (exe) | 模式3：Web服务端部署 |
|------|-------------------|---------------------|-------------------|
| **本质** | 静态HTML + 本地JSON | 桌面壳 + 内嵌后端 | 前后端分离 + 服务端数据库 |
| **启动方式** | 双击 index.html | 双击 exe | 浏览器访问URL |
| **数据存储** | 本地JSON文件 / IndexedDB | 本地SQLite / 文件 | PostgreSQL / 云端数据库 |
| **网络依赖** | 无 | 无 | 有（必须联网） |
| **后端服务** | 无 | 内嵌（Electron/Tauri） | 独立（FastAPI） |
| **多人协作** | ❌ 不支持 | ❌ 单用户 | ✅ 支持 |
| **文件访问** | 受限（浏览器沙箱） | 完整（原生API） | 通过服务端中转 |
| **安装成本** | 零 | 需安装/解压 | 零（客户端），需运维服务器 |
| **更新方式** | 替换文件 | 自动更新/重装 | 服务端热更新 |
| **数据安全** | 用户完全控制 | 用户完全控制 | 服务器托管 |
| **扩展能力** | 低 | 中 | 高 |

## 模式1：本地文件网页（当前架构）

### 架构形态

```
┌─────────────────────────────────┐
│  浏览器打开 index.html           │
│  ┌──────────────────────────┐  │
│  │ 纯前端 SPA（原生 JS）     │  │
│  │ - 画布渲染（Canvas 2D）    │  │
│  │ - 数据逻辑（ES6 Modules）  │  │
│  │ - 本地状态管理            │  │
│  └──────────────────────────┘  │
│              │                   │
│  通过 fetch() 读取本地 JSON     │
│  通过 File System Access API   │
│  或 Blob 下载保存文件           │
│              │                   │
│  本地文件系统（IP定义、设计文件）│
└─────────────────────────────────┘
```

### 数据模型

| 概念 | 存储形式 |
|------|---------|
| IP 定义 | `data/ip_catalog.json`（IP 数组） |
| Block Design | `data/designs/{name}.json`（每个设计一个文件） |
| BD Cell | 嵌入在 design JSON 中 |
| BD Connection | 嵌入在 design JSON 中 |
| Address Region | 嵌入在 design JSON 中 |
| 接口模板 | `data/interface_templates.json` |

### 关键技术点

- **文件读取**：`fetch()` 加载项目目录下 JSON；`<input type="file">` 加载外部设计文件
- **文件保存**：File System Access API（Chrome/Edge）直接写入；其他浏览器使用 Blob 触发下载
- **IP Catalog**：从本地 `data/ip_catalog.json` 加载，导入时追加新 IP
- **导出产物**：生成 `.json` 设计文件与 `.tcl` 脚本

### 优点

- **零安装、零配置**：无需 Python、PostgreSQL、Docker
- **数据完全本地**：无需担心数据泄露或服务器宕机
- **离线使用**：没有网络也能工作
- **文件级版本控制**：设计文件可用 Git 管理

### 缺点

- **浏览器安全限制**：无法直接访问任意文件路径（需要用户选择目录）
- **性能受限**：大量 IP 时前端渲染卡顿
- **无协作**：无法多人同时编辑一个设计
- **功能受限**：复杂算法（地址分配优化、高级 DRC）在前端实现成本高
- **浏览器兼容**：File System Access API 仅 Chrome/Edge 支持

### 适用场景

- 个人快速查看/编辑 IP 定义与 Block Design
- 轻量级设计浏览工具
- 无需后端的离线环境

## 模式2：桌面应用（未来方向）

### 架构形态

```
┌──────────────────────────────────────────┐
│  桌面应用窗口（Electron / Tauri / Native）│
│  ┌────────────────────────────────────┐  │
│  │ 渲染层：UI + 画布（同前端技术）      │  │
│  │ - 原生 JS + Canvas 2D               │  │
│  └────────────────────────────────────┘  │
│  ┌────────────────────────────────────┐  │
│  │ 主进程：内嵌后端服务                 │  │
│  │ - Node.js 或 Rust 后端              │  │
│  │ - 本地 SQLite 数据库               │  │
│  │ - 完整文件系统访问                  │  │
│  └────────────────────────────────────┘  │
│  本地文件系统（设计文件、IP库、生成产物）│
└──────────────────────────────────────────┘
```

### 两种技术路线

| 路线 | 技术栈 | 说明 |
|------|--------|------|
| **Electron** | 前端 + Node.js后端 + SQLite | 成熟生态，体积大（~150MB） |
| **Tauri** | 前端 + Rust后端 + SQLite | 轻量（~5MB），性能更好，但 Rust 学习曲线 |

### 优点

- **原生体验**：快捷键、右键菜单、拖拽文件、系统托盘
- **完整文件访问**：像 Vivado 一样直接操作文件系统
- **离线使用**：无网络也能完整工作
- **性能**：本地 SQLite 足够快，前端渲染流畅
- **数据本地**：用户完全控制数据位置

### 缺点

- **体积大**：Electron 应用通常 100MB+
- **跨平台打包**：Windows/Mac/Linux 需要分别构建
- **更新维护**：需要自动更新服务器或手动下载

### 适用场景

- **主力工具**：像 Vivado 一样作为工程师日常设计工具
- **企业内网**：无互联网环境的离线工作站
- **IP 封装**：本地 IP 开发、封装、验证的完整工作流

## 模式3：Web服务端部署（未来方向）

### 架构形态

```
┌────────────────────────────────────────────┐
│  浏览器访问 https://ipm.company.com         │
│  ┌──────────────────────────────────────┐  │
│  │ 前端 SPA（原生 JS / Vue / React）      │  │
│  │ - 画布渲染、UI交互                      │  │
│  │ - 通过 HTTP API 与后端通信              │  │
│  └──────────────────────────────────────┘  │
│              │ HTTP / WebSocket              │
│  ┌──────────────────────────────────────┐  │
│  │ 服务端（Docker 容器）                   │  │
│  │ - FastAPI（Python）                     │  │
│  │ - PostgreSQL 数据库                     │  │
│  │ - 文件存储（对象存储/本地卷）            │  │
│  └──────────────────────────────────────┘  │
│              │                               │
│  云端/服务器（数据库、文件、计算资源）        │
└────────────────────────────────────────────┘
```

### 架构优势

- **团队协作**：多用户同时编辑、评论、版本历史
- **集中管理**：企业级 IP 库统一管控、权限控制
- **计算扩展**：复杂 DRC、地址优化可在服务端高性能计算
- **数据安全**：服务器备份、审计日志、灾难恢复
- **随时随地**：任何设备、任何地点访问（VPN/公网）
- **CI/CD 集成**：与自动化构建流水线集成

### 缺点

- **网络依赖**：无网络无法工作
- **数据不在本地**：数据在服务器上，导出才能本地使用
- **运维成本**：需要服务器、数据库、备份、安全维护
- **延迟**：大设计文件加载有网络延迟

### 适用场景

- **企业级 IP 管理平台**：全公司统一 IP 库和设计管理
- **团队协作**：分布式团队、多人同时设计
- **云原生**：与 CI/CD、DevOps、云平台集成

## 三种模式对当前设计的影响差异

### 如果保持在模式1（当前架构）

| 当前组件 | 变化 | 工作量 |
|---------|------|--------|
| 本地 JSON 文件 | 继续使用，无需改动 | 无 |
| 前端服务层 | 持续迭代 | 持续 |
| Canvas 画布 | 继续优化 | 持续 |
| 后端数据库 | 无 | 无 |
| 部署 | 直接打开 `index.html` | 无 |

### 如果未来切换到模式2（桌面应用）

| 当前组件 | 变化 | 工作量 |
|---------|------|--------|
| 前端代码 | 保留，放入 Electron/Tauri 壳 | 低 |
| 数据存储 | JSON 文件 → SQLite（可选） | 中 |
| 文件访问 | 从浏览器沙箱改为原生文件 API | 中 |
| 后端 | 新增内嵌后端（可选，用于复杂计算） | 中 |
| 打包 | 增加 Electron/Tauri 构建流程 | 中 |

### 如果未来切换到模式3（Web 服务端）

| 当前组件 | 变化 | 工作量 |
|---------|------|--------|
| PostgreSQL 数据库 | 新增 | 高 |
| FastAPI 后端 | 新增 | 高 |
| 前端 | 保留画布/UI，HTTP API 通信 | 中 |
| 数据模型 | JSON 文件 → 关系型 + JSONB | 高 |
| 部署 | Docker + CI/CD | 中 |

## 建议决策路径

### 当前阶段（v1.0.0）：**模式1 本地文件网页**

- 已完成，作为 MVP 验证核心概念
- 零依赖、易分发、易演示
- 适合个人用户与轻量使用

### 未来可选方向

| 阶段 | 目标 | 模式选择 | 说明 |
|------|------|---------|------|
| **v1.0.0** | 验证核心概念 | 模式1（当前） | 纯前端，已完成 |
| **v1.1.0+** | 增强单用户体验 | 模式2（桌面应用） | 完整文件访问、原生体验 |
| **v2.0.0+** | 企业级团队协作 | 模式3（Web 服务端） | 多用户、权限、审计、CI/CD |

---

## 总结

| 模式 | 复杂度 | 工作量 | 适用场景 | 建议 |
|------|--------|--------|---------|------|
| **1. 本地文件网页** | 低 | 已完成 | 轻量查看、个人设计、离线环境 | **当前架构，v1.0.0 采用** |
| **2. 桌面应用** | 中 | 中等 | 主力设计工具、离线使用 | **未来方向** |
| **3. Web 服务端** | 高 | 大 | 团队协作、企业级 | **远期方向** |

**核心建议**：
1. v1.0.0 以模式1 纯前端形式发布，验证并完善核心设计能力
2. 后续如需增强单用户体验，可迁移至模式2（Electron/Tauri 桌面应用）
3. 如面向企业级团队协作，再考虑模式3（Web 服务端）
4. 三种模式共享同一套前端画布与数据模型设计，便于未来迁移
